# Every refusal of the CLI, and of AgentFlow

The `agentflow-app` CLI prints a refusal as `<CODE>: <message>` on stderr (exit `1`; `2` for a usage error). Find the code below, read what it means, and do what the last column says. `lint` problems (lowercase codes such as `bare_key`) are in `lint-problems.md`.

## Printed by the CLI

| Code | Printed by | Means | Do |
|---|---|---|---|
| `USAGE` | any | an unknown command or flag, a missing argument, `--from` with `--prefix`, `--key`, `--no-ui` or `--no-site`, a `--parameters` or `--decisions` file that cannot be read or is not a JSON object, or a `--decisions` file holding anything but grant declines, `--parameters` or `--decisions` with `--sandbox`, a `sandbox` action or flag it does not take, a `--as` handle that is not one of the sandbox's people, or `sandbox create` while `.agentflow/sandbox.json` names a live sandbox (exit 2) | read the usage it prints |
| `APP_FILE_MISSING` | `build` | no `agentflow.app.mjs` in this folder | run it in the project's folder |
| `APP_FILE_INVALID` | `build` | `agentflow.app.mjs` fails to load, takes a member `defineApp` does not, or a workflow graph is broken (`add open_case to ORDER`) | fix that file or that graph |
| `CONFIG_VERSION_MISSING` | `build` | no `configVersion` in `config/package-manifest.json` | add `"configVersion": 1` first |
| `CONFIG_VERSION_UNKNOWN` | `build` | a `configVersion` this SDK does not read | install the SDK release it names |
| `BUILD_REFUSED` | `build`, `lint` | a config problem, `<file>#<pointer>: <reason>`, or a file it cannot read | fix that place (the authoring skill) |
| `PACKAGE_STALE` | `build --check`, `lint` | `package/` is not what `config/` builds | run `pnpm build` and commit `package/` |
| `PACKAGE_MISSING` | `seal`, `deploy`, `types` | no `package/`; from `types`, also a manifest object with no file under `objects/` | run `pnpm build` |
| `TYPES_STALE` | `types --check` | `src/generated/app.ts` is missing or not what `package/` generates | run `agentflow-app types` and commit the file |
| `UI_TOOL_MISSING` | `build` | the manifest declares a UI module, and Vite is not installed | `pnpm add -D vite`, or remove `ui` |
| `UI_BUILD_FAILED` | `build` | Vite failed on the module | fix the module's error |
| `UI_ENTRY_MISSING` | `build`, `seal` | the built module has no `index.js`; from `seal`, the manifest declares `ui` and `package/ui/` was never built | make the Vite build write `index.js`; before `seal`, run `agentflow-app build` |
| `UI_ENTRY_INVALID` | `build` | `index.js` does not end with `export { mount };` | export `mount`, as the starter's module does |
| `UI_FILE_TYPE` | `build` | a built file the platform does not serve (it names the extensions allowed) | keep only those files, and no HTML |
| `KEY_EXISTS` | `keygen` | a key already exists there | keep it, or choose another `--key-id` |
| `KEY_ID_INVALID` | `keygen`, `seal` | an empty key id or one with whitespace; `keygen` also refuses an id outside letters, digits, `.`, `_`, `-` (at most 64, starting with a letter or digit) | use a plain name of that shape |
| `KEY_MISSING` | `seal` | no ed25519 key in `keys/`, or no file at `--key` | run `keygen`, or fix `--key` |
| `KEY_AMBIGUOUS` | `seal` | more than one ed25519 key in `keys/` | pass `--key <file>` |
| `KEY_PERMISSIONS` | `seal` | the key file can be read by others | run the `chmod 600` it prints |
| `KEY_INVALID` | `seal` | the file is not an ed25519 key in PKCS#8 PEM | pass the `.pem` that `keygen` wrote |
| `SEAL_FILE_UNLISTED` | `seal`, `lint` | `package/` holds a file outside `manifest.json`, `objects/` and `ui/`, or a dotfile such as a macOS `.DS_Store`, or a symlink | remove it (Finder adds a `.DS_Store` to any folder it opens) |
| `SEAL_PATH_INVALID` | `seal`, `lint` | a file path a package may not hold | rename it |
| `SEAL_MANIFEST_MISSING` | `seal` | no `package/manifest.json` | run `pnpm build` |
| `SEAL_MANIFEST_INVALID` | `seal`, `deploy` | the manifest is not JSON, or its `id` is not `<prefix>/<key>` | fix `id` in the config, then build |
| `SEAL_VERSION_INVALID` | `seal`, `deploy` | `version` is not SemVer 2.0 | write `1.0.0` style |
| `SEAL_JSON_INVALID` | `seal` | a file under `objects/` is not JSON | run `pnpm build`; never edit `package/` |
| `SEAL_LIMIT_EXCEEDED` | `seal` | more than 1998 files, a file over 5,000,000 bytes, over 100,000,000 bytes in all, or an archive over 20,000,000 bytes | make the package, usually its UI module, smaller |
| `SEAL_OUT_EXISTS` | `seal` | that version is sealed already, with other contents (the message ends: if that version never reached a deployment or the catalog, delete the file and seal again) | raise `version`; if that version was never stored by `deploy`, `publish` or the packages page (`lint` stores nothing), delete the old `.afpkg` and seal again (`upgrading-the-sdk.md`) |
| `SEAL_ARCHIVE_INVALID` | none today | a sealed archive that cannot be read | |
| `INIT_DIR_NOT_EMPTY` | `init` | the folder exists and is not empty | name a new or empty folder |
| `INIT_NAME_INVALID` | `init` | the prefix or the key breaks the rule it prints | fix `--prefix` or `--key` |
| `INIT_DIR_UNWRITABLE` | `init` | the folder cannot be written | choose a folder you can write |
| `INIT_STARTER_INVALID` | `init` | this install of the builder has no usable starter | reinstall the builder at a release tag |
| `DRAFT_INVALID`, `DRAFT_UNSUPPORTED`, `DRAFT_REBUILD_DIFFERS` | `init --from` | see the `agentflow-from-draft` skill | |
| `SEAL_MISSING` | `deploy` | no sealed file for this version in `dist-app/`, or no file at `--file` | run `pnpm seal`, or fix `--file` |
| `DEPLOY_NOT_CONFIGURED` | `lint`, `deploy`, `sandbox` | `AGENTFLOW_URL` or `AGENTFLOW_TOKEN` is not set (`AGENTFLOW_SANDBOX_KEY` for `sandbox` and `deploy --sandbox`), `AGENTFLOW_URL` is not a URL, the address is not `https://`, or holds a user, a query or a fragment | set what it names (Connecting to AgentFlow) |
| `DEPLOY_UNREACHABLE` | `lint`, `deploy` | nothing answered at the address, it redirected, or what answered is not AgentFlow (a proxy refusing the archive as too large shows here too); `--wait` gives up after five dropped answers in a row | check `AGENTFLOW_URL` and your network; after a redirect, use the address it names; for a 413, ask whoever runs the proxy to raise its limit |
| `DEPLOY_FAILED` | `deploy` | the install failed (it prints AgentFlow's problem), or the deployment was cancelled: withdrawn, or replaced by a newer one; or the last 20 deployments of this release with these settings all ended | read the problem (an install that failed names only the run: `after-deploy.md`), fix it or ask the admin, then deploy again; after 20 ended deployments, seal a new version, change the settings (`--parameters` or `--decisions`), or retry after their idempotency keys expire |
| `SANDBOX_SPEC_MISSING` | `sandbox`, `deploy --sandbox` | there is no `sandbox.json` in this folder | add the file that declares the sandbox's people, groups and install answers, or run it in the project's folder |
| `SANDBOX_SPEC_INVALID` | `sandbox`, `deploy --sandbox` | `sandbox.json` fails the check, `sandbox.json: <field>: <message>`, with the wording AgentFlow itself uses | fix that member, then run `sandbox check` again |
| `SANDBOX_SECRET_MISSING` | `sandbox`, `deploy --sandbox` | the environment variable a connection's `secret_env` names is unset or empty | set that variable, and run it again |
| `SANDBOX_STATE_TRACKED` | `sandbox`, `deploy --sandbox` | git tracks a file under `.agentflow/`, the folder that holds the sandbox's keys; or `.gitignore` cannot be read or written, so the folder cannot be kept out of git | run `git rm -r --cached .agentflow`, commit that, and keep `/.agentflow/` in `.gitignore`; for an unreadable or read-only `.gitignore`, fix the file's permissions |
| `SANDBOX_STATE_MISSING` | `sandbox` | there is no `.agentflow/sandbox.json` in this folder, so it has no sandbox of its own | make one with `sandbox create`, or name a sandbox with `--id` where the command takes it |
| `SANDBOX_STATE_INVALID` | `sandbox`, `deploy --sandbox` | `.agentflow/sandbox.json` is not the version 1 file this CLI writes | delete the sandbox it names with `sandbox delete --id <id>` if it is still live, remove the file, and make the sandbox again |
| `SANDBOX_OPEN_FAILED` | `sandbox open` | no browser could be started where the CLI runs (a bare SSH session, a CI job); it never prints the sign-in link, and the one it asked for expires unused in 5 minutes | run `sandbox open --as <handle>` on a machine with a browser; a test signs in with `signInAs` instead |
| `DEPLOY_STALLED` | `deploy` | the install stayed `installing` for 5 minutes | check that a worker is running, and that its `APP_GRANT_SOURCE_WRITES_ENABLED` matches the API's; the sandbox stays for inspection |
| `INTERNAL` | any | a fault in the builder, not in your app | run again with `AGENTFLOW_APP_DEBUG=1` to print its stack, and report it to the AgentFlow team |

## Refusals from AgentFlow

The guide's troubleshooting page, `<AGENTFLOW_URL>/guides/en/xay-dung-ung-dung/khac-phuc-su-co` (Vietnamese `<AGENTFLOW_URL>/guides/xay-dung-ung-dung/khac-phuc-su-co`), lists these for people reading without an agent.

`lint` and `deploy` print AgentFlow's own refusals with its code, `<CODE>: <message>`, exit `1`. A refused key (401 or 403) adds a line telling you to check `AGENTFLOW_TOKEN`; for `sandbox` commands and `deploy --sandbox` the key is `AGENTFLOW_SANDBOX_KEY`, and the line says to check that.

| Code | Means | Do |
|---|---|---|
| `INVALID_TOKEN` | the key is unknown, revoked or expired | ask an admin for a new key, and set `AGENTFLOW_TOKEN` again (`AGENTFLOW_SANDBOX_KEY` for `sandbox` and `deploy --sandbox`) |
| `FORBIDDEN` | the key's principal may not do this: `deploy` needs `integration.admin`; `sandbox` and `deploy --sandbox` need `sandbox.create`, which is opt-in only: no built-in role holds it | ask an admin to give the principal a role with it (for `sandbox.create`, a role the admin makes and grants) |
| `PLATFORM_TOO_OLD` | this deployment is older than the package's `minPlatformVersion` | ask the AgentFlow team to upgrade the deployment, or deploy to one that runs that version. Lowering `minPlatformVersion` works only down to the value this SDK release states, never below it: edit `minPlatformVersion` in `config/package-manifest.json`, build, seal (raise `version`, or delete the sealed file, if this version was sealed before: `SEAL_OUT_EXISTS`), then deploy |
| `APP_PACKAGE_PROBLEMS` | the upload has lint problems; it prints each one | run `lint`, fix them, raise `version` or delete the refused file from `dist-app/` (it was never stored), build, seal, deploy |
| `PACKAGE_SIGNATURE_INVALID` | the file changed after it was sealed | seal again |
| `PACKAGE_LIMIT_EXCEEDED`, `PACKAGE_ARCHIVE_INVALID`, `PACKAGE_MANIFEST_INVALID` | the archive breaks a limit, is not a package archive, or its manifest is refused; the message names which | as for the `SEAL_` code of the same meaning |
| `APP_CATALOG_PREFIX_HELD` | another organization already publishes under this prefix (409) (from `publish`) | use your own prefix, or ask the AgentFlow operator |
| `APP_CATALOG_PREFIX_RESERVED` | the prefix is `af`, `agentflow`, `rfx` or `reflexify`, which only the organization the operator names may claim (403) (from `publish`) | choose another prefix |
| `APP_CATALOG_VERSION_EXISTS` | that version is in the catalog already with other content (409). Rare from `publish`: its upload answers `APP_PACKAGE_VERSION_EXISTS` first | raise `version`, build, seal, publish |
| `APP_CATALOG_BACKPORT_REFUSED` | the version is at or below the newest one in the catalog (409) (from `publish`) | raise `version` above it |
| `APP_CATALOG_NOT_PUBLISHER` | your organization does not hold the package's prefix, so it may not withdraw that version (403) (from `withdraw`) | withdraw only versions your organization published. A key without `app_catalog.publish` (and, for `publish`, `integration.admin`) is `FORBIDDEN` instead: use a key whose role has them |
| `APP_CATALOG_SANDBOX_REFUSED` | a sandbox organization cannot use the catalog (403) (from `publish`, `withdraw`) | publish with a key of the real organization |
| `APP_CATALOG_VERSION_WITHDRAWN` | a setup or activation chose a catalog version that was withdrawn since (409); it comes from the install, or from `deploy --wait`'s failure, never from `publish` (sending a withdrawn version's bytes again prints `withdrawn <id> <version>` and exits `1`) | choose the latest published version, or deploy your own upload of it |
| `APP_PACKAGE_VERSION_EXISTS` | your organization already holds this version with other content. The same content signed again (a new key, say) is accepted. A version that already held two contents from before this rule cannot be uploaded again either | raise `version` in `config/package-manifest.json`, build, seal, deploy (deleting the sealed file does not help: the earlier release is stored) |
| `APP_GRANT_RECIPIENT_COLLISION` | the setup page lists it under "Problems the plan found" and the plan cannot be approved: the admin picked the same group for two parameters that each give a grant on the same entity | pick different groups for them (members may overlap); the parameter's `help` should say so (the authoring skill, `pitfalls.md`) |
| `APP_STEP_FAILED`, `APP_DEPENDS_ON_FAILED` | on the setup page under "Problems the plan found", as `APP_STEP_FAILED  <object key> · <pointer>` and one `APP_DEPENDS_ON_FAILED  <object key>` for each object that needs the failed one. Setup writes the whole package into a scratch copy of the organization to plan it; a step that fails leaves a finding, and what depends on it is skipped. The pointer is the failing step's own code. The admin cannot approve until none is left | read the pointer. `DUPLICATE` is a **name the organization already holds**: see the next row. Any other pointer is the failing command's own code, as `<code>` or `<code>:<node>.<field>` for a workflow graph: fix what it names in `config/`, raise `version`, build, seal, deploy. Fix the `APP_STEP_FAILED` rows first: the `APP_DEPENDS_ON_FAILED` ones go with them |
| `DUPLICATE` (the pointer of an `APP_STEP_FAILED`) | a workflow's `name` (the display name in its config, not its key) or an agent's `name` is already used in the target organization. The organization keeps one workflow per name, compared without regard to case, **archived workflows included**, and one agent per name likewise. The row names the package's object key, never the name that clashes. A key clash is a different refusal (`WORKFLOW_KEY_TAKEN`): installed keys carry the package's prefix, so only an earlier install of this very package id can clash. A workflow with no `name` in its config is named after its prefixed key, so it practically never clashes. A sandbox starts empty and `lint` cannot see the organization, so neither warns. | the simplest fix is the team's: change the object's `name` in `config/`, raise `version`, build, seal, deploy (the plan is made again each time the setup page opens). The admin can instead rename the live object that holds the name. An archived workflow holds its name for good (nothing restores, renames or deletes it), so the team must rename theirs; an archived agent can be restored in Admin → Agents and then renamed. Before the first deploy, ask the admin whether the names your workflows and agents use are free (`admin-message.md`) |
| `APP_RELEASE_UNAVAILABLE` | the release an install run was prepared for could not be loaded again when the run activated: it is no longer stored for the organization, its stored archive changed, its signature entry is malformed, it no longer verifies, or it is not the release that was approved. A deployment that ends `failed` with this `type` carries `detail: the install run <run id> failed` and nothing else: it names the run, never the reason | ask the deployment's operator to look in the server's log for `app install run failed for good` with that run id, which holds the reason, and to check that every worker on that database runs the same build as the API. Then read the deployment (`after-deploy.md`), and `deploy` again only after that: it makes a new deployment that needs approval again |
| `STAGE_TRANSITION_NOT_ALLOWED` | after install, a run failed with `the move from 'X' to 'Y' is limited to: a member of group 'G'`: the workflow's run-as service principal is not in the group the stage move is limited to. Setup cannot see this (its only warning is that the principal needs record access, "gets it only once it is in one of: <groups>"); it shows at run time | an admin adds the principal to group G from the **Groups** card on the service principal's page (Admin → Service principals; Admin → Groups does not list service principals), then retries the run or starts it again |
| `APP_VERSION_NOT_NEWER` | a higher version is installed, or the same version with other content | raise `version` above it |
| `VALIDATION_ERROR` | the deploy request holds a parameter the manifest does not declare, or a decision other than declining one of this package's grants; the message names each | fix the key in `parameters.json`, or leave that decision to the admin who approves on the setup page |
| `APP_DEPLOYMENT_NOT_FOUND` | while waiting, the deployment is not in the key's organization | check `AGENTFLOW_URL` and `AGENTFLOW_TOKEN` did not change; open the link it printed |
| `SANDBOX_LIMIT_REACHED` | your organization already holds the most live sandboxes it may (10 by default) | `agentflow-app sandbox list`, then `sandbox delete --id <id>` for one you do not need, or wait for one to expire; `deploy --sandbox` replaces this folder's own first, so a loop holds one |
| `SANDBOX_NESTING_REFUSED` | the key belongs to a sandbox: a sandbox cannot make a sandbox | use a key of your real organization in `AGENTFLOW_SANDBOX_KEY`, not one of a sandbox's |
| `SANDBOX_CONNECTION_SHARED` | a connection in `sandbox.json` uses a provider account that is already connected in another organization, and event routing would send that organization's events into the sandbox | give the sandbox a Resend account of its own, and set the variable `secret_env` names to its key |
| `SANDBOX_NOT_LIVE` | the sandbox is expired, deleted or being purged, so it takes no sign-in | `deploy --sandbox` makes a new one |
| `CONNECTION_TEST_FAILED` | on a sandbox create: Resend refused the key (a key limited to sending is the usual cause), rate limited it, or the webhook could not be registered. No sandbox is left behind | use a full-access Resend key in the variable `secret_env` names, and run it again |
| `EMAIL_FROM_DOMAIN_UNVERIFIED` | a connection's `settings.from` is on a domain its Resend account has not verified | verify the domain in that Resend account, or change `from` in `sandbox.json` |
| `APP_ARM_REFUSED` | arming the installed app's triggers was refused, with a line for each trigger and what holds it back. The app stays installed, with every trigger off | fix what each line says (an unready connection, a missing setting), then arm again: in a sandbox, `sandbox open --as <handle>` as its owner and use the receipt's **Turn on triggers** in **Admin → Apps**, or run `deploy --sandbox` again |
| `APP_GRANT_SOURCE_WRITES_DISABLED` | the API has `APP_GRANT_SOURCE_WRITES_ENABLED` off, so a plan that writes grants stays prepared and the install cannot finish (503) | ask the AgentFlow team to turn `APP_GRANT_SOURCE_WRITES_ENABLED` on for the API and the workers alike |
