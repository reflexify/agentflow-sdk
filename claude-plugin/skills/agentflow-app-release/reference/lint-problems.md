# What `lint` reports, and what to do

`pnpm exec agentflow-app lint` sends `package/` to AgentFlow, which checks it with its own rules and prints one
line per problem:

```
bare_key  workflow "workflow:open_case"  /inputSchema/properties/c/x-entity: "@obj:entity:case" is not a key sentinel; a key position takes the key form (fix: …)
```

The line is `<code>  <object kind and key>  <JSON pointer inside that object>: <message> (fix: <fix>)`; a problem about the whole object has no pointer. The pointer
is into the built object under `package/objects/`, not into `config/`: find the same place in the config file
that makes the object (`entity:case` is `config/entities/case.json`, `workflow:open_case` is a workflow in
`config/build/`). Fix it there, run `pnpm build`, and lint again until it prints `no problems`. A problem never
blocks `pnpm build`: only `lint` and the upload see it. `lint` does not judge an entity's field values (`type`,
`format`, `format_options`, constraints) or a view's `config`, apart from option colours: `pnpm build` checks a field's
values (all but a constraint's `pattern` as a regular expression and a checklist's columns), and AgentFlow checks the rest when the
package is installed, so keep to the values `entities.md` lists, and expect a mistake there to surface on the
admin's setup page or when the install is activated.
`lint` cannot tell whether a group you grant to sits inside the manifest's `audience`, because the group is a
parameter the admin answers at install: the setup page warns `members_outside_audience` instead, since members of
a group outside the audience get no app listing and no module (`manifest.md` in the authoring skill).

A package may also print `warning: unattended_placement_only  workflow "<key>"  /runAs: …` on stderr after the lint, for `unattended_placement_only`. It is not a problem and never changes the exit code (`--json` carries it as `warnings`): a workflow runs as a service principal parameter, one of its record steps needs an operation the manifest grants that parameter only at `placement` or `placement_subtree`, and a service principal reaches records at those scopes only once an admin places it in a unit. A grant to `everyone` does not help: Everyone is every active person, never a service principal. The warning judges only the grants that name the run account's parameter itself: a grant to a group the account sits in is not seen, so a group granted `organization` does not silence it, and a group granted only `placement` does not raise it. Place the run account in a unit after the install, or grant the parameter itself `organization`, or a `unit` scope anchored at a `unit_ref` parameter, on that entity.

A package may print `warning: email_egress_not_by_connection` too: a `connection_ref` parameter that an Email step or an email trigger (`config.object_type` beginning `email.`) is bound to has no `egress` entry naming it by connection. It is not a problem and never changes the exit code. Email goes to whichever provider the admin connects, and setup admits only the hosts `egress` lists, so an app that lists one provider's host is refused at setup once pointed at another. Add `{ "connection": "${param:<key>}", "purpose": "…" }` to `egress` in `package-manifest.json` (the builder writes `@param:<key>`), and no provider's host. Keep the host entry only when the app is meant to work with one provider.

A package with signing steps may also print `warning: …` lines about signing methods. They are not problems: they say the deployment does not offer a method the package signs with, so its setup lists Electronic signing or Certificate signing as unavailable and refuses to install the package, and they never change the exit code (`signing.md` in the authoring skill).

## Problems you can cause from `config/`

| Code | Means | Do |
|---|---|---|
| `uuid_literal` | An id (a UUID) is written into the package, as a value or as a member name. An id names something in one organization. | Bind it through a parameter (`${param:…}`), or name the object by a reference (`${entity:case}`). Two things are not this problem: the platform entities Users and Units (write them by the ids `entities.md` gives, and the builder turns them into references), and the ids an object gives its own parts, which lint leaves alone and which stay fixed in the file: a view's preset ids (`config/presets/*/id`) and inline metric ids, a dashboard's tile and measure ids. A related list's `summary_metrics` entry is left alone only when it is the inline metric id of a view the list is bound to; a catalogue metric there is `${entity_metric:<entity>/<key>}`, so an id that names no inline metric of a bound view is this problem. A dashboard measure's `entity_metric_id` always is: follow the metric by key with `metric`. |
| `bare_key` | A position that takes a *key* holds a bare key or an id-form reference. These positions are an `x-entity` in a workflow's `input_schema`, a workflow variable's `entity`, and a relationship step's key. The builder writes the key form of a start form's `x-entity`, so a `bare_key` there means a package built by hand or by an older builder: rebuild it. The builder cannot write the key form of a workflow variable's `entity` or a relationship step's key. | Write `"x-entity": "<entity key>"` in an `input_schema` or an entity's `create_form` and the builder writes the key form (an `input_schema` picker only validates: no launch form is drawn from it, `workflows.md`, "Start forms"). |
| `installed_key_literal` | A string holds this package's installed prefix (`acme_case_desk__…`), the key an object gets in one organization: someone copied it out of an installation. | Name the object with a reference (`${entity:case}`), never with its installed key. |
| `slot_not_parameter` | A value that differs per organization is written as a literal: the identity a workflow runs as, a secret, a connected account, a person, group or unit in a Human step's assignment, an agent's model or access group. | Declare a parameter of the right type in the manifest and write `${param:<key>}` there. The types are in `manifest.md`. |
| `parameter_undeclared` | `${param:x}` is used, and the manifest declares no `x`. | Add `x` to `parameters`, or fix the name. |
| `parameter_type_mismatch` | A parameter is used where its type does not fit: a `user_ref` as a group, a `text` as a secret, a `text` as the unit a record step files into (`destinationUnit`). | Use a parameter of the type that position takes (`manifest.md`), or declare one. |
| `agent_parameter_optional` | The parameter that holds an agent's model or access group has `required: false`. An agent with no value would run on the deployment's default or on no one. | Set `"required": true` on that parameter. |
| `run_as_not_initiator` | People can start the workflow (a start grant, an entity action, or a Call from one that people start), and it does not run as `initiator`. | Run it `INITIATOR`. A workflow nobody starts by hand is a separate workflow with a trigger (`workflows.md`, "Who a workflow runs as"). |
| `run_as_not_service_principal` | A trigger starts the workflow, and it does not run as a `service_principal_ref` parameter. | `servicePrincipal("<param key>")`, with the parameter declared. |
| `run_as_conflict` | People start the workflow and a trigger starts it too: one `runAs` cannot serve both. | Make two workflows: one people start (initiator), one a trigger starts (service principal). |
| `group_hold_missing` | A trigger groups its events (`config.group`) and the workflow waits on people (a Human or Signature step, directly or through a Call). | Set `config.group.hold_while_waiting` to `true`. |
| `call_cycle` | Workflows call each other in a cycle. | Remove one Call, or move the shared work into a workflow neither calls back. |
| `formula_cycle` | Computed fields read each other in a cycle. | Make one of them read a stored field. |
| `rollup_member_unknown` | A rollup, or a rollup `filter`, holds a member it does not take. | A rollup is `inverseKey`, `agg`, optionally `field` and `filter`; a filter entry is `{ field, op, value }` (`entities.md`). |
| `rollup_inverse_unresolved` | No reference field of the package targets this entity and declares the rollup's `inverseKey` as its `inverse_key`. | Add the child entity's reference field with that `inverse_key`, or fix `inverseKey`. |
| `profile_link_invalid` | An `inverse_key` on a reference to Users that is not a profile link (a list of users, `recommendedSecured`, no `natural_key` of its entity over the field alone, a handle that is not a local key or that a user field or another field of the package already has), or any `inverse_key` on a reference to groups or units. | Keep it a single reference, add a `natural_key` entry whose `fields` is this field alone, and choose a handle of its own; remove `inverse_key` and `inverse_label` from a reference to groups or units. |
| `creator_default_invalid` | A field's `default` is `{ "kind": "creator" }` and the field cannot take it: it is not a `reference` or `reference_list`; it references groups or units; or it references an entity of this package that is not a profile entity (none of its fields, or more than one, is a single reference to Users with an `inverse_key`). The pointer is `/default`. A reference to another package's entity is not judged here: the install judges it. | Keep the default on a reference to Users (it fills the creator) or to a profile entity (it fills the creator's record there, `entities.md`). Give the referenced entity exactly one profile link, or remove the default. |
| `work_clock_without_policy` | A deadline clock names no SLA policy. | Declare an `sla_policy_ref` parameter and set the clock's `sla_policy` to `${param:<key>}` (`work.md`). |
| `work_record_unit_anchor` | A unit pool in a routing rule is anchored at the record's unit (`"anchor": { "type": "record_unit" }`), and the entity does not declare `requires_unit_classification: true`. A record of an unclassified entity has no unit to anchor on. | Add `requires_unit_classification: true` to the entity, or anchor the pool at a `unit_ref` parameter: `"anchor": { "type": "fixed", "unit_id": "${param:<key>}" }`. |
| `grant_unit_scope_unclassified` | A grant on one of the package's own entities uses `placement`, `placement_subtree`, or an anchored `unit` / `subtree`, and the entity does not declare `requires_unit_classification: true`. Those scopes are relative to a person's unit or to one unit, and an entity with no units has none. The pointer is `/grants/<i>/operations/<operation>` in the manifest. A grant on an entity another package owns is not judged here: the install judges it. | Add `requires_unit_classification: true` to the entity, or grant `own` or `organization` instead. |
| `unit_field_key_taken` | An entity that declares `requires_unit_classification: true` also declares a field of its own keyed `unit`. The platform adds the `unit` field itself, so the two would collide. | Rename your field. Rules, views and stage gates name the platform's field by the key `unit`. |
| `seed_on_classified_entity` | An entity that declares `requires_unit_classification: true` ships `seed` records. A starter record would have to be filed in a unit the package cannot name. | Remove the entity's `seed`, or remove `requires_unit_classification`. |
| `unit_written` | Something in the package writes `unit` on an entity that declares `requires_unit_classification: true`: a form property bound to it (`"x-entityField": "unit"`) that is not `readOnly`, at `/schema_json/properties/<name>`, or an Entity Record step whose `body` binds it, at `…/parameters/body/<i>` (inside a For Each too). `unit` is set by the platform from the creator's unit or the step's `destinationUnit`; a package never writes it, and AgentFlow refuses the package when it verifies it. `pnpm build` refuses the step binding and a create form bound to `unit` before lint sees them, so this means a package edited by hand or made by `pack` from a draft. | Remove the binding, and name where a created record is filed with the step's `destinationUnit` (`steps.md`, "The unit a created record is filed in"). A form that shows the unit marks the property `"readOnly": true`. |
| `work_module_page_without_ui` | An entity's `work.module_page` names a page of the package's module, and the package declares no `ui`. | Declare the package's `ui` module, or remove `work.module_page`. |
| `work_module_page_invalid` | An entity's `work.module_page` is not a page of the module: it must start with `/`, hold `{{ record_id }}` (spelt exactly so) at most once and no other `{{` or `}}`, and pass the launcher's path rule, counted with the record's id in place of the placeholder. | Write it as a module path such as `"/items/{{ record_id }}"` (`work.md` in the authoring skill). |
| `work_dependency_missing` | An entity's `work` declares a member without the member it needs: `assignable` and `deadline` need `lifecycle`, `work_surface` needs `assignable`, `module_page` needs `work_surface`. | Declare the member it names, or remove the one that needs it. |
| `required_field_unbound` | A field is `required`, and the entity's create form does not bind it: no property of the form's schema carries `"x-entityField": "<field>"`, or only a `readOnly` one does. The install refuses that create form, since a person could not fill the field (before this rule it reached the setup page as `APP_STEP_FAILED  entity:<key> · VALIDATION_ERROR`). The message names the form. | Add the field to the create form, or drop `required`. A field with a default, such as a people field that defaults to the creator, is filled without the form, and grants that scope on it still work. |
| `tile_position_invalid` | A dashboard tile's size or column is outside what its kind takes (before this rule it reached the setup page as `TILE_POSITION_INVALID`). The message names the member, its value and the kind's limits: today a text tile is 4–24 columns wide and 3–12 rows tall, a number 3–12 × 5–10, a list 6–24 × 5–40 and a chart 6–24 × 6–30, and `col + w` is at most 24. The message is the platform's own table, so trust it over this line. | Give the tile a position inside those limits. |
| `option_color_unknown` | An enum option's `color` is not one of the palette's names (`gray`, `sky`, `teal`, `amber`, `emerald`, `violet`, `indigo`, `rose`, `fuchsia`) or a `#RRGGBB` hex, on an entity's field or a field of an extension (before this rule it reached the setup page as one `APP_STEP_FAILED` on the field among an `APP_DEPENDS_ON_FAILED` for everything that needed it). | Use a palette name (`emerald` for green, `rose` for red) or a `#RRGGBB` hex. The builder refuses it too, at `pnpm build`. |
| `reference_binding_invalid` | A form property bound to a reference field is not a picker AgentFlow accepts: a list field's `"format": "entity"` sits on the array instead of under `items`, a single reference has no `"format": "entity"`, or the property names no `x-entity`. | For a list write `{ "type": "array", "items": { "type": "string", "format": "entity" }, "x-entity": "<entity>", "x-entityField": "<field>" }`; for one reference `{ "type": "string", "format": "entity", "x-entity": "<entity>", "x-entityField": "<field>" }`. |
| `display_field_invalid` | An entity's `display_field` names a `reference`, `reference_list`, `file` or `list` field, which holds no value a record can be named by (before this rule it reached the setup page as `APP_STEP_FAILED  entity:<key> · VALIDATION_ERROR: display field '<key>' must be a scalar field`). | Name a `text`, `auto_number` or `formula` field instead. A formula can read a field of the record a reference points to, so a record can still be named after what it refers to. |
| `requirement_undeclared` | The package uses a platform entity (Users, Groups, Units), or an organization's agent or skill, that `requires` does not declare. | Add it to `requires.entities` (`user`, `group`, `org_unit`) as the case desk's manifest does. |
| `requirement_unused` | `requires` declares something no object or grant uses. A package with a `ui` module is never told this: lint cannot see what the module reads, so an entry the module or a site needs stays. A package with no module is, even when its standalone site reads that entity through the directory, and `deploy` is refused with it. `org_unit` is in use whenever an entity declares `requires_unit_classification`: its `unit` field reads it, and a template names the unit through it. | Remove the entry. With a `ui` module, keep what the module or site reads: lint does not report it. A package with no module cannot keep an entry that only its standalone site reads: add a `ui` module, or make that read from a site registered outside the package (no ceiling). |
| `egress_undeclared` | A Webhook step sends a secret to a host the manifest's `egress` does not list. An email step or a connected-app trigger is never judged here: its provider is the admin's choice, and setup checks the hosts of the connection chosen. | Add `{ "host": "<the step's host>", "purpose": "…" }` to `egress` in `package-manifest.json`. |
| `destination_unknown` | A secret is sent to a URL whose host cannot be known before the package runs (a template in the scheme or host), or to a provider AgentFlow has no client for. | Write the URL with a fixed host and declare it in `egress`; use a supported provider. |
| `sql_node` | The workflow has a SQL step, which names one organization's database connection. | Remove the step; reach the data through an entity. |
| `agent_inline_tools`, `agent_inline_mcp`, `agent_inline_knowledge` | An agent step carries its own tools, MCP servers or knowledge documents: ids of one organization or deployment. | Refer to an agent of the package with `agentRef` and leave these out (`agents-and-skills.md`). |
| `agent_profile_mcp`, `agent_profile_knowledge` | An agent's `profile` carries MCP servers or knowledge documents. | Remove them; the organization attaches its own after installing. |
| `agent_ref_not_sentinel` | An agent step's `agentRef` is not `{ "agentId": "${agent:<key>}" }` of an agent of the package, or it carries `narrowing` or an `overrides.model`. | Write `agentRef: { agentId: "${agent:<key>}" }` only. |
| `read_limit_invalid` | An agent's `read_limit` entry names a built-in directory entity (users, groups, units), an entity twice, an empty or repeated `operations` list, or is the 201st entity. The pointer is `/read_limit/entities/<i>`. | Name each entity of the package once, with `read`, `list` or both (`agents-and-skills.md`, "What the agent may read"). |
| `learn_agent_not_own` | A Learn step's `agent_ref.agentId` is not an agent of the package. | Name the package's own agent: `${agent:<key>}`. |
| `learn_read_limit_missing` | A Learn step's agent declares no `read_limit`. | Give the agent a `read_limit` that covers what the step reads. |
| `learn_read_limit_uncovered` | One problem per gap between what the Learn step reads and its agent's `read_limit`: an operation on an entity the limit lacks, or a type in `learn.types` missing from `read_limit.memory_types`. The message says what to add. | Add the operation on that entity to `read_limit.entities`, or the type to `read_limit.memory_types`. |
| `agent_read_limit_uncovered` | An Agent step gives its agent the run's subject (a `subject.record…` or `subject.selection` path, or a thread on `{{ subject.record_id }}`), and the agent's `read_limit` does not list `read` on the workflow's subject entity. Every run of the step would fail with `AGENT_CEILING_DENIED`. The pointer is `/nodes/<i>/parameters/agentRef`. | Add `read` on that entity to the agent's `read_limit.entities`, or leave `read_limit` out if the agent is not meant to be restricted (`agents-and-skills.md`, "What the agent may read"). |
| `memory_definition_invalid` | A memory type or relationship that the memory designer would refuse (a title naming no field, a bad `search_on`, a field of the wrong kind), or one key declared as both a type and a relationship. The message is the designer's own. | Fix the definition as the message says (`memory.md` in the authoring skill). |
| `memory_reference_invalid` | A Learn step, a `memorySave` or a `read_limit.memory_types` entry names no memory type or relationship of the package; or a Learn step or `memorySave` names one the package ships `deprecated`; or a Learn step lists a relationship with an end it neither binds nor lists a type for. | Name a definition of the package with `${memory_type:<key>}` or `${memory_relationship:<key>}`, drop the deprecated one, or list the end's type in `learn.types`. |
| `memory_save_read_limit_uncovered` | An agent with `profile.memorySave` does not read a type it saves into (or a type end of a relationship it saves). One problem per type. | Add the type to the agent's `read_limit.memory_types`. |
| `source_path_unknown` | An entity's `source` names a stream AgentFlow does not know (it is neither an ERP object like `purchase_order` nor a stream a connector offers, such as `contacts`), or a path the stream's record does not have: a `from`, a reference's `key` or `line` part, `lines.from`, a line's `key` part or an item's `from`. The pointer is the path (`/source/stream`, `/source/fields/<field>/from`, `/source/lines/key/0`). An ERP stream is checked against the ERP model's field list, with a line's and a list item's paths read from their own record (`lines.erp_line_id`, `lines.taxes.rate`); a native stream's path is `properties.<name>`. A HubSpot property an account defines itself is not here: the admin's setup page checks it against the connected account. `^path` reads the parent record and means something only inside `lines`. A valid `custom.<key>` is accepted, with a type lint cannot judge, at three places only: in the header's `fields`, as a line's own path inside `lines`, and as `^custom.<key>` inside `lines`. Inside a list mapping's `items`, or as a header path that walks into a line's `custom` (`lines.custom.<key>`), it is refused here, since setup and the guard on the connection's custom fields would never see it. | Correct the stream or the path. The ERP model's paths are listed by `GET /admin/integrations/categories/erp/metadata`; a native stream's are its connector's properties (`properties.email`). |
| `source_type_mismatch` | A mapped path's type does not pair with the entity field it fills, or `lines.from` or an `items` list reads a path that is not a list. The pairs are: text into text; an enum into a text or enum field; a decimal or integer into a number field; a boolean into a boolean; a date or datetime into a date or datetime; a list of objects into a `list` field through `items`. The message names the path's type and the field. | Map the path into a field of a type the message allows, choose another path, or change the field's type. A copy of an object, or of a list without `items`, has no field to land in: map a path inside it. |
| `source_enum_unmapped` | The stream can send an enum option that is neither an option of the entity's enum field nor a key of the mapping's `values`. One problem per mapping, at `values` (or at `from` when it has none), naming every option left. An ERP's open sets end in `other`, which needs a place too. | Add each option to the field's `enum_values`, or map it in `values` onto an option that exists. A value with no place would fail its record when it arrived. |
| `source_key_mismatch` | A reference's `key` has a different number of parts from the key paths of the stream it points into (an ERP stream is keyed by two: `company_erp_id` and `erp_id`), or its `line` has a different number of parts from the target lines entity's `key`, or it has a `line` and its target is not a lines entity. The pointer is the `key` or the `line`. | Give one path per key part of the target's stream, in order, and `""` for a part the record does not have (a currency has no company). Give `line` only when the target is a lines entity, one path per part of its `key`. |
| `connection_category_mismatch` | A connection parameter's `category` cannot serve the place it is bound: an Email step's `connection` takes `email`, an Integration step's `connection` `crm` or `erp`, a connected-app trigger's `config.account` `crm`, `email` or `erp`, an entity source's `connection` `crm` or `erp`. On an `erp` parameter it also fires at an Integration step's `objectType` or `operation`, a trigger's `config.object_type` and a source's `stream` that are not canonical ERP objects (and `get`, `search` or `upsert`). | Bind a parameter of a category the place takes, or change the parameter's `category`. On an `erp` connection name a canonical object (`purchase_order`, `vendor_bill`, ...). |
| `connection_category_missing` | An Integration step's `connection` is bound to a `connection_ref` parameter that declares no `category`. The step's object and operation mean something only on one kind of connection, and setup offers the parameter every connection. Email steps, triggers and sources may leave the category out. | Add `category: "crm"` or `"erp"` to the parameter. |
| `signing_no_field` | A Human step with `signing` signs documents that declare no signing field, so the signer has nowhere to sign or fill: its `signing.documents` templates, or, when it lists none, its own form. The pointer is `/nodes/<i>/parameters/signing`. | Add a signing field (a `signature` item with a `role` in the template's content) to a document template the step signs, or to the form when the step signs its own. |
| `signing_role_unknown` | A `signature` step has a signer whose `roleKey` is not the `role` of any signing field in its documents, so the signer's seal has nowhere to land. One problem per role. The pointer is `/nodes/<i>/parameters/signers`. | Add a signing field with that `role` to the document template, or change the signer's `roleKey` to a role the template has. |
| `signing_role_uncovered` | A signing field in a `signature` step's documents has a `role` that no signer holds, so nobody could sign it. One problem per role. The pointer is `/nodes/<i>/parameters/signers`. | Add a signer for the role, or remove the role's signing field from the document template. |
| `signing_cert_no_anchor` | A step signs with `signingMethod: "client_cert"`, and the fields that seal would land on are all typed fill fields (text, date, number, checkbox): a signer's role in a `signature` step, the step's documents in a Human step. A certificate seal needs a signature or initials field to anchor on. The pointer is `/nodes/<i>/parameters/signers` or `/nodes/<i>/parameters/signing`. | Make one of the role's fields a `signature` or `initials` field, or sign with `server_email`. |
| `signing_signer_not_one_person` | An internal signer of a `signature` step is not exactly one person: a group, a unit pool, several candidates, none, or a rule whose backup is a group, a unit pool or another rule. A group is an audience, not a signer. The pointer is `/nodes/<i>/parameters/signers/<n>/recipient/assignment`. | Name one person: a `user_ref` parameter, or a rule whose backup is one user. |
| `signing_decline_route_invalid` | A signing step's `onDecline` names somewhere the step cannot go, or the manifest asks for a platform older than the route. A `signature` step's route is `{"kind": "branch", "edgeIds": […]}` and a Human step's `signing.onDecline` may also be `{"kind": "action", "actionId": "…"}`; the problem is raised when the route names no edge, names more than one (a route follows one edge; insert a Fork to fan out), names an edge that does not leave the step (in a loop, the loop body's edges), an edge an action, the timeout or the end condition already owns, or every edge that leaves a `signature` step; when a `signature` step also sets `failOnSignerFailure: false`; when an `action` route is on a `signature` step, names an action the step lacks or names the signed one; or when the route does not read. A route also needs `minPlatformVersion` of `2026.11` or later, because an older deployment drops the route unread: a signed `signature` step would follow the route's edge too, and a Human step would fail on a decline. The pointer is `/nodes/<i>/parameters/onDecline` or `/nodes/<i>/parameters/signing/onDecline`. | Draw an edge of its own from the step for a decline to follow, or name an action other than the signed one, and put its id in the route; remove `failOnSignerFailure: false` when the step has a route; set `minPlatformVersion` to `2026.11` or later. |
| `notifications_platform_too_old` | The manifest declares `notifications` and its `minPlatformVersion` is older than `2026.11`. An earlier build refuses the member, so the package would fail at upload on that deployment. The pointer is `/minPlatformVersion`. | Leave `minPlatformVersion` for the builder: it raises it to `2026.11` when the package declares `notifications` or holds a `notify` step, so a stale value means `package/` was built by hand or by an older SDK. Rebuild (`notifications.md` in the authoring skill). |
| `task_page_without_ui` | A Human step names a `page`, and the package declares no `ui`. The pointer is `/nodes/<i>/parameters/page`. | Declare the package's `ui` module, or remove the step's `page` (`workflows.md`, "A page for the step", in the authoring skill). |
| `task_page_invalid` | A step's `page` is not a task page: the step is not a Human step; or the path is not a page of the module (it must start with `/`, hold `{{ record_id }}` at most once and no other `{{` or `}}`, and pass the launcher's path rule); or the mode is not `redirect` (`embedded` is reserved). The pointer is `/nodes/<i>/parameters/page`. | Put the page on a Human step, write a module path such as `/review/{{ record_id }}`, and set the mode to `redirect`. |
| `task_pages_platform_too_old` | A step names a `page` and `minPlatformVersion` is older than `2027.02`. An earlier build ignores the page without a word, so every task would open in AgentFlow's own view. The message is "Task pages need platform 2027.02 or later". The pointer is `/minPlatformVersion`. | Set `minPlatformVersion` to `2027.02` or later. The builder does it for you, so a stale value means `package/` was built by hand or by an older SDK: rebuild. |
| `manifest_mcp_removed` | The manifest carries `mcp`. AgentFlow no longer reads the member, and every package built by an SDK older than this change writes `{ "enabled": false }` there, so this is what you meet on such a package. The pointer is `/mcp`. | Update the SDK, delete `mcp` from `config/package-manifest.json` (the builder now refuses the member) and run `pnpm build` again. To ship a workflow switched on as a tool, set `tool_enabled` on the workflow instead (`workflows.md` in the authoring skill). |
| `workflow_tool_requirements_unmet` | A workflow with `tool_enabled: true` misses what the **Callable as a tool** switch asks of an installed workflow, so the install could not switch it on. The message holds one sentence for each miss: no description; an End step that maps no output (it names them); a trigger of the package starts the workflow (the sentence names those triggers); or the workflow runs over a set of records. The pointer is `/toolEnabled`. | Do what each sentence says: write a `description`, give every End step an `outputs` mapping, remove the package's trigger for that workflow (or make a second workflow the trigger starts), or start the workflow on no record or one record. If the workflow is not meant to be a tool, remove `tool_enabled` (`workflows.md`, "Shipping a workflow as a tool"). |
| `ceiling_uncovered` | A step or a trigger of the package asks for something the app's ceiling does not allow. Every run of the app's workflows meets that ceiling, the ones the app launches and the ones a trigger, a schedule or a work escalation starts: one that asks for more fails (`APP_CEILING_DENIED`) or parks on the field (`field_not_readable`), and a trigger's filter and mappings read an undeclared field as absent. Lint checks the declaration before a run meets it, and the install plan and the installed app's needs attention name what a workflow asks beyond it. The ceiling is what the manifest declares: the package's own entities (all of them, less `ceiling.narrow`), each `requires.entities[]` entry and each `requires.packages[].access` entry, at the declared `access` (`read` covers read and list; `write` also create and update) and for the `fields` it lists, and the package's own extension fields at read on the entity each extends (named by their installed key, `<prefix>__<field>`): reading one is never reported, and setting one always is, since a source fills it. A step is judged by what it does: an Entity Record step's operation on an entity (a get, search or list of the built-in users, groups and units included, at the `fields` their `requires.entities` entry lists), an Entity Relationship step's update of the entities at both ends of its relationship (of a relationship the package ships; a dependency's is judged at install), a Human step's entity view and the update and field reads of a bound form, each field the step names (a body, filter or sort entry, or a search's `fields`), and each field a `subject.record…` path in the step reads through the package's own reference fields and a classified entity's `unit`, the unit's `name` and `code` included (`{{ subject.record.unit.name }}` needs `name` listed in `requires.entities[org_unit].fields`). A record trigger is judged by reading its entity and the fields its filter, input mappings and group key name: a mapping names a field as `event.<field>` or `event.event.previous.<field>` (event metadata such as `event.event.record_id` names none), and a filter names a field it reads, a before-value's field, and a field whose change `{"in": ["<field>", {"var": "event.changed"}]}` asks about. The pointer is the step in the workflow (`/nodes/<i>`, a step inside a loop at `/nodes/<i>/parameters/body/nodes/<j>`) or the member of the trigger (`/config/entity_id`, `/config/filter`, `/config/input_mappings/<i>/from`, `/config/group/by/field`); one problem is reported for each thing missing. Not judged: a write to the built-in users, groups and units, which publishing refuses, a `subject.record` path past an inverse handle or an entity that is not the package's own, a related record's fields, a conversation check, a Learn step's source, a Start step's subject, a computed field's inputs, and what a workflow of another package does when this one calls it. | Declare what the step or trigger uses: list the field in `requires.packages[].access[<entity>].fields` (or `requires.entities[].fields` for an organization's entity), raise that entry's `access` to `write` for a create or an update, or declare the entity if it is not declared. For the package's own entity, remove the entry in `ceiling.narrow` that takes it away. Then run `pnpm build` again. |
| `skill_name_too_long` | The installed skill name (`<prefix>-<package key>-<skill key>`, with `_` written `-`) is over 64 characters, ends or doubles a hyphen, or is not lowercase letters and digits. | Shorten the skill's key or the package key; do not end a skill key in `_`. |
| `body_invalid` | AgentFlow refused the shape of one object. The message is `PACKAGE_BODY_INVALID` and the object's kind, with no pointer. At a dashboard measure's `entity_metric_id`, its `metric`, or a member beside `metric`, it has a pointer and its own message: the measure names a metric by an id, follows a key the package does not ship on the entity the tile measures, or carries something beside the key other than `id`, `primary`, `key` and `color` (the metric's definition is the metric's). Typical causes: a workflow's `runAs` that is not `initiator` or a service-principal parameter; a step that is not an object; an agent whose `model` is not a `text` parameter, whose name or description has blanks at either end, or whose restricted access names no group; a skill description with blanks at either end; a view `type` AgentFlow does not know. | Compare the object with its description in the authoring skill's reference files, and fix that member in the config file. |
| `manifest_invalid` | AgentFlow refused the manifest: a member of the wrong shape. The message names the pointer. | Fix it in `config/package-manifest.json` (`manifest.md`). |
| `platform_too_old` | This deployment runs an older version than `minPlatformVersion`. Or, with the message "Entity metrics, and a dashboard tile that follows one, need platform 2027.03 or later", the package ships an entity metric, or a dashboard measure follows one by `metric`, and `minPlatformVersion` is older than `2027.03`. | For the first, see `PLATFORM_TOO_OLD` in `refusals.md`. For the second, set `minPlatformVersion` to `2027.03` or later; the builder does it for a package that ships a metric, so a stale value means `package/` was built by hand or by an older SDK: rebuild. |

## Problems the builder does not let you make

These need a member, or a pair of members, the builder never writes, so you meet them only in a package built another
way (a hand-edited `package/`, which `pnpm check` refuses): `trigger_enabled` (a trigger must ship with `enabled:
false`; the builder always does), `field_secured` (a field shipped with `sensitive: true`; a package may only
recommend securing a field, which the builder writes as `recommendedSecured: true`),
`field_queried_and_recommended_secured` (a field with `queriedByApp: true` and `recommendedSecured: true` together:
the app filters or sorts on it, so it cannot also be recommended for securing; the build refuses the pair at
`/fields/<n>/queriedByApp`, and the fix is to leave out `queriedByApp` if the app does not filter or sort on the
field, or `recommendedSecured` if it does), `export_not_owned`, `dependency_undeclared`, `dependency_unused`,
`feature_reference_from_core` and `feature_requirement_undeclared` (exports, dependencies and features, which the
builder leaves empty).
