# Changelog

Each release of the AgentFlow SDK is a tag `sdk-vX.Y.Z` on both
`reflexify/agentflow-sdk` and `reflexify/agentflow-app-template`. Its section says which
`configVersion` and package `formatVersion` it writes, the oldest AgentFlow platform version
it needs, and the result of running the skills on a fresh copy of the template.
Its `Skills dry run:` line names every skill the dry run covered, and the release check refuses a line that leaves out a skill the plugin ships.

## Unreleased

On the platform, `{{ now() }}` renders to the millisecond (`2026-11-03T18:54:44.945+07:00`) where it wrote up to nine fractional digits; a whole second still renders without a fraction. The authoring skill's `workflows.md` says so.

`host.navigate(path, { replace: true })` takes the place of the current history entry, so Back skips a page that only redirects (a task's `/tasks/<id>` that opens its order). The standalone host, AgentFlow's host and a module element all pass it on; an AgentFlow built before it ignores the option and adds an entry, so a module can pass it everywhere. `AppNavigateOptions` is the new type. It makes no contract version: `APP_CONTRACT_VERSION` stays 4.

`build --check` and `types --check` compare text, not bytes, so a Windows checkout whose line endings `core.autocrlf` turned into CRLF no longer reports `PACKAGE_STALE` or `TYPES_STALE` for an unchanged `package/` or `src/generated/app.ts`. `build` also reads a Code step's file (`config/code/*.js`) and a skill (`config/skills/*.SKILL.md`), the only text files it embeds in an object, with CRLF as LF, so a CRLF copy of either builds the same objects and seals to the same digest; before, it built other objects, `build --check` named them stale and `seal` gave another digest. A built UI module (`package/ui/`, and `ui/built/` of a converted draft) is still compared and hashed as bytes. The starter ships a `.gitattributes` (`* text=auto eol=lf`), so a project made with `init` checks out LF everywhere; an existing project adds the same file (`upgrading-the-sdk.md`), and `init --from` now writes it too.

The builder refuses three mistakes AgentFlow refused only at install: an enum option `color` outside the palette (`gray`, `sky`, `teal`, `amber`, `emerald`, `violet`, `indigo`, `rose`, `fuchsia`, or `#RRGGBB`); an `end()` output that is a JSON literal (`lit(true)`; write `lit("true")`), and any output that is not a `ref`, `tpl` or string `lit`; and a routing rule's `when` in which an object applies other than one JSONLogic operator, such as a rule's `{ join, leaves }`. A `when` naming an operator the engine does not know still builds and is refused at install.

From the inno/pl author's second feedback: the builder refuses `$bind` in a rule's field leaf, in a `was` test and in a comment's `closed_when`, which AgentFlow refuses at install (a rule as `ENTITY_VALIDATION_RULE_INVALID: … compares against a binding, which a write cannot resolve`, a `closed_when` as `VALIDATION_ERROR: closed_when: …`); the builder README and `rules-and-stages.md` used to list it as a rule value. A package can carry parallel arms. `fork(id, name, [edgeIds])` and `join(id, name)` in `@reflexify/agentflow-app-builder/workflow` write a Fork, whose arms are named `arm_1`, `arm_2` and so on, and a Join, which waits for every arm and takes no options. `merge` counts a Fork's arm edges as its own and refuses at build what publish would refuse at install: a Fork with fewer than two arms, an arm with other than one edge, two arms to one step, a Fork that reaches no Join, a Join no Fork reaches, and a Human, Decision or routed Signature step feeding a Join directly. It also refuses a Join with a member besides `id` and `label`, such as `wait`, which AgentFlow would ignore. Publish still pairs each Fork with its Join at install and refuses arms that share a step, and a Fork/Join in a For Each body that has no End. A draft with a Fork converts with `init --from`, where it used to fail `DRAFT_UNSUPPORTED`.

`merge` accepts a loop that publish runs, where it used to refuse every cycle (`loop through a -> b`): one entered at one step, with no loop inside it, holding only Human, Agent, Decision, Document, Email, Webhook, Set Variable, Fork, Join, Extract Text, Image, Learn, Entity Relationship, Code and Notify steps. Any other loop is refused with the step or the entries it names (`x (entity_record) is inside the loop through …`, `the loop through a, b is entered at a, b`, `… holds another loop`). The authoring skill's `workflows.md` gains "Parallel arms: Fork and Join" and "Sending work back: a loop".

`webhook(id, name, { url, method?, headers?, body?, auth?, retries? }, settings?)`, `extractText(id, name, source, { mode?, format?, onOversize? }, settings?)` and `integration(id, name, { connection, operation, objectType, identityField?, mappings?, delivery?, captureTo?, associations?, safeFieldPaths? }, settings?)` write those steps and refuse at build a value outside each kind's set, what publish refuses (an empty `url` or `source`, a `get` or `upsert` with no `identityField`, an `upsert` that maps no value to it, a `captureTo` outside `vars.` and `input.`, an inline `delivery` on a read), what AgentFlow would ignore (any `delivery` on a read, an `operator` outside a `search`), and the wire names (`bodyMode`, `secretId`, `provider`, `externalAccountId`) with the option that means them. `webhook` writes the designer's `webhook` config, with `auth.secret` the key of a `secret_ref` parameter. `examples/document-check` is a data-only app that reads a submission's document with `extractText` and looks its code up with a `webhook` that sends a secret to a host in `egress`, branching on a 404 under the error strategy `continue`. `steps.md` lists the three, with what each outputs.

An entity field may carry `recommendedSecured: true`, which asks the organization to secure the field; the install plan warns until it does. The builder used to refuse it, although lint's `field_secured` told authors to write it. `sensitive` is still refused, now with a message that names `recommendedSecured`. A field may reference Groups (`ffffffff-0000-0000-0000-000000000002`, written `@req:entity:group`, with `group` in `requires.entities`), which AgentFlow has taken since 2026-10-14: a group in a people field stands for its members in a record scope. The authoring skill's `access.md` gains "Fields only some people may read" and the Groups field that lets some groups see only the records that need them; `entities.md` says a formula reads one field through a reference, and `work.md` how several targets fit a clock's four.

A package can add fields to another package's sourced entity and have the sync fill them from the ERP's custom fields. The new config folder `config/entity_extensions/` holds one file for each extension, named for its `key`: `key`, `extends` (`${dep:rfx/erp-core#entity:vendor}`, of a package in `requires.packages` with an `access` entry for that entity, `read` being enough), `fields` and `source: { fields }`. A field is inline, with `key`, `type` (`text`, `number`, `boolean`, `date`, `datetime` or `enum`), `label`, `description`, `enum_values` and `recommendedSecured`; it is never `required` and has no formula and no default. Each field has exactly one copy in `source.fields`, `{ "from": "custom.<key>", "values"?: {…} }`, and every copy names a field. The build writes `objects/entity_extension/<key>.json`, lists `entity_extension:<key>` in the manifest's `objects`, never exports it, and refuses a second extension of one entity. It refuses what package verification refuses and names the pointer: an `enum` with no `enum_values` or another type with them, a null `label` or `description` (leave them out), a `from` that is not `custom.<key>` (a canonical path, a `^` path, a key with `__`), a `ref` or `items`, a field with no copy or a copy that names no field, a `values` entry that lands on no option, an `extends` whose package is not in `requires.packages` or has no `access` entry for the entity, and a file whose name is not its `key`. A package with an extension needs platform `2026.11`: the builder raises `minPlatformVersion` to `EXTENSIONS_PLATFORM` (`2026.11`), a later month stays, and an older AgentFlow build refuses the kind at upload. `types` leaves the kind out of the generated keys, since `GET /app/objects` never lists it. The field is installed under the package's prefix as `<prefix>__<key>` (`rfx_ap_match__risk_rating` for the package `rfx/ap-match`), and the package's own formulas, views and workflows name it by that key. Setup adds one required checklist item for each extension: `extension_target_not_sourced` when the entity has no source, and `custom_field_not_mapped` or `custom_field_type_mismatch` against the connection of the source that fills it. An install, an upgrade that changes the copies, a reattach and turning the app on again queue every record the source has applied, so records synced before the extension get the value; an upgrade that changes a field's type is blocked (`extension_field_type_changed`), and a field the release drops, or a whole extension it drops, stays on the entity as the organization's, with its values. Undo deletes the extension's fields with their values and detach leaves them as the organization's. The authoring skill's `reference/entities.md` gains "An extension", and its `manifest.md` and the `rfx/erp-core` README no longer send a custom field on `erp-core`'s record to an entity of your own with a source; `init --from` converts no extension, since a draft carries none.

A Signature step's task stays with its signer. `reassign_work` and `assign_work` of such a task now answer 409 `SIGNATURE_TASK_NOT_REASSIGNABLE`, so a module that hands tasks on should offer neither for a task whose step `kind` is `signature`; release and claim still work, and a released task can only come back to its signer. The signing frame is given only to the person the envelope line was addressed to, so a task someone else holds cannot be signed. The generated API types gain the 409 on both operations.

`submit` refuses a Signature step's task with `SIGNATURE_TASK_REQUIRES_SIGNING` (400). Such a task completes only through signing; a submit used to close it unsigned while the step went on waiting for that signer, so sign it with `host.signing?.sign(…)` or in AgentFlow.

A Signature step that cannot create its envelope for a reason with a code now fails at once with that code, for example `SIGN_INTERNAL_RECIPIENT_UNRESOLVED` for a signer field that names a group, `SIGNATURE_NO_FIELD`, or `BAD_REQUEST` for a document it cannot read. The run detail's `error_code` shows the code. Before, the step was retried until its job ran out of attempts and was recorded as `STEP_FAILED`.

A module embedded in AgentFlow can ask the host to sign: app contract 3 adds an optional `signing` member to `AppHost`, `sign({ entity, record })`, which opens AgentFlow's signing dialog (the inbox's task pane) for the open signing task of the app's own workflows that `record` names, or is about, and resolves `signed` (the step's signature is recorded; on a Signature step with several signers, when the last of them signs), `declined` (the envelope was declined before this person's signature was recorded, by this person or another signer), `closed` (the dialog closed with no end yet, or the step ended without a signature or a decline; read the record again later or use `host.realtime`) or `nothing_to_sign` (no open signing task of this app was found for the target). The workflow moves on after `signed` or `declined` through its own job, so a record read made at once may still show the old state. `record` is the Workflow task's own record or a record the task is about, and "about" means the run's subject: a signing step whose documents come from another record, in a run about something else, is not found by that record and resolves `nothing_to_sign`. The new types are `AppSignTarget`, `SignOutcome` and `AppSigning`. `APP_CONTRACT_VERSION` is 3 and `contractVersion` is typed `3`, so a host written against contract 2 that sets `contractVersion: 2` no longer type-checks; set it from `APP_CONTRACT_VERSION`. `defineModuleElement` forwards `signing`; the standalone host has none, so call it as `host.signing?.sign(…)` and offer "Sign in AgentFlow" otherwise. AgentFlow's host offers `signing` to every module it mounts, whatever contract it declares. A package whose module calls it declares `ui.contract: 3`, which an AgentFlow built before contract 3 refuses at verification (an older API) or shows as unsupported (an older frontend), so the API and frontend ship together. In the API elements, `<agentflow-provider>` takes `signing` as a property, and `<agentflow-task-detail>` shows a Sign button for a signature task, or a signing step the person holds, when it is set, and emits `agentflow-signed` or `agentflow-declined` with `{ recordId, entityId }`; without it the task detail shows today's notice, and so it does after a `nothing_to_sign`, until the step is read again. The `agentflow-ui-module` skill gains `reference/signing.md`, and the authoring skill's "Where people sign" now says how a module signs.

An installed app's token may now upload a file when it names what the file is for: send `entity_id` and `record_id` as text parts beside `file`, with `field` for a File field of that record or `comment=true` for a comment on it. The file is held to that target until it is first bound, so only a write of that field on that record, or a comment on that record by the same person, takes it, and until then the app may read the file while it may read the target, so a site can show what it just uploaded. An upload is refused before anything is stored or its idempotency key is claimed when the target is missing or malformed or names a field that is not a File field (`VALIDATION_ERROR`), lies outside the ceiling (`404`) or is one the app may not write (`APP_CEILING_DENIED`), is a record the person may not read or update (`ENTITY_RECORD_NOT_FOUND`), or is a comment thread that is off or closed (`COMMENTS_DISABLED`, `COMMENTS_CLOSED`). A module embedded in AgentFlow calls as the person, whose target parts are ignored, so one request serves both hosts. The generated API types gain the four optional parts on `AttachmentUpload`, and the shared `Unprocessable` response is gone, since the upload was its only user. The directory answers an app's token too, at the fields its package lists in `requires.entities` (the generated types for this came with sdk-v0.7.0, whose notes did not say so): `get_group` with the `group` entity (its members only while the package requires `user` as well), `resolve_identities` for the people and groups whose entity is listed with `name` (never service principals), and `list_units` and `get_unit` with `org_unit`. Their answers widen to `GroupDetailResponse` (`GroupDetail | AppDirectoryGroup`), `UnitDirectoryPage` (`UnitPage | AppUnitPage`) and `DirectoryUnitResponse` (`DirectoryUnit | AppDirectoryUnit`); `resolve_identities` keeps its shape. An AgentFlow build older than 2026.11 refuses an app's upload, and may refuse the directory reads, so a package that relies on them sets `minPlatformVersion: 2026.11`.
