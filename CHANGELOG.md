# Changelog

Each release of the AgentFlow SDK is a tag `sdk-vX.Y.Z` on both
`reflexify/agentflow-sdk` and `reflexify/agentflow-app-template`. Its section says which
`configVersion` and package `formatVersion` it writes, the oldest AgentFlow platform version
it needs, and the result of running the skills on a fresh copy of the template.
Its `Skills dry run:` line names every skill the dry run covered, and the release check refuses a line that leaves out a skill the plugin ships.

`sandbox.json` takes `sla_policies`, the SLA policies a sandbox is made with, and an install parameter names one as `@sla_policy:<key>`, so `deploy --sandbox` installs an app whose work has a deadline clock in one step, with no policy id to find and no script to make one. `sandbox check` checks a policy as AgentFlow does (a key, a name of 1 to 80 characters unique ignoring case, four targets on one base) and refuses `@sla_policy:` given to another kind of parameter. The new sandbox's policy ids are in `.agentflow/sandbox.json` under `ids.sla_policies`, and `readSandbox` returns them. `escalation_policies` does the same for escalation ladders, named as `@escalation_policy:<key>`: an `assign` step names its assignees by the file's keys (`@group:`, `@unit:`, `@person:`), and a step that starts a workflow is refused, since the workflow comes with the install. A `within` filter, in a view, a preset or a dashboard tile, takes two more windows: `before_today`, every day before the organization's today, and `after_today`, every day after it; neither includes today. An overdue view or count is now `due within before_today` beside the open statuses, and the skills' overdue recipes say so. `build` accepts both. Leave the comparison off an overdue count. A tile comparing with `previous_period` over either window alone is refused at install, because neither has a length; with a bounded window on the same field, such as `this_month`, the overlap has one and it is accepted. `previous_year` is accepted too, but on a single number it counts the records overdue by more than a year, so it reads meaningfully only on a chart split by a date bucket. An AgentFlow build older than this release refuses both windows at install, and `minPlatformVersion` is a month, so check the deployment's release before relying on them.

## sdk-v0.6.0

formatVersion: 1
minPlatformVersion: 2026.10
Skills dry run: 2026-10-31, one pass on a fresh copy of the template made from this branch's SDK (a local mirror tagged sdk-v0.6.0, installed by git reference) — agentflow-app-authoring, agentflow-app-release, agentflow-ui-module and agentflow-from-draft (a facilities desk, `acme/facilities`, written from the skills alone: a request entity with a file field and a location entity with starter records (`seed`), access for requesters and a facilities group, a stage model and a rule that fixes the location once the request exists, a workflow started by a `created` trigger with an Agent step reading the new request and its photo and a Human step that ends itself on the record's status (`endWhen`), an update that claims the request only while nobody holds it (`expect` on an empty field), a view and launcher entries with the gear icon, and a UI module with its own typeface through `loadFonts`, a record's runs and a run's trace, and the package's agents over 30 days; `build`, `types`, `typecheck`, `test`, `build --check`, `sandbox check`, `keygen`, `seal` twice (`unchanged:` the second time), `lint` and `deploy` up to `DEPLOY_NOT_CONFIGURED`, AgentFlow's own lint rules run offline on the sealed package (`app-package lint`, no problems); and `case-desk.zip` through `init --from`, rebuilt to the same package with its workflow rewritten with the helpers); 18 findings, 15 fixed in this release (among them `build` refusing an `endWhen` branch's edges, and no skill saying that a later step cannot read who decided a Human step, filed as agentflow-7pld), 3 low ones left (`init --help` printing every command, the empty-module warning shown only at `init --from`, guide pages that need a deployment to open); not covered: `lint` against a running deployment, the sandbox loop, `deploy`, the install plan, `status`, `publish`, a run of the workflow and anything in AgentFlow's web pages (there was no deployment and no browser).

A rule made only of `is_update` and `changed` (or `changed_any`), such as a field fixed once the record exists, now greys that field on the record page, with the rule's message, for every reader; it was offered and refused on save. A rule of `is_update` and `changed` of the status field greys the record's moves the same way. The skills say so.

The kit exports `loadFonts(faces)`, which registers a module's own typefaces on the page, because a shadow root ignores `@font-face`. It adds each face once per page, across modules, skips a family the host already provides, resolves when the faces load, and warns instead of rejecting when one does not. The UI-module skill's typeface pitfall uses it.

A launcher entry, an entity or a sidebar group can use the icon `settings`, a gear; AgentFlow now has 40 icon names, and `build` no longer warns about this one. A deployment older than this release does not know it: a launcher entry draws a dot, an entity the database icon and a group the folder. `minPlatformVersion` is a month, so `2026.10` is the floor to set, but it does not tell an earlier October deployment from this one: check the deployment's release before relying on the gear.

Run detail carries a failure's stable code. The generated API types gain, on a run's detail (`InstanceDetail`), `error_meaning` and `withheld` beside its `error_code`; on each step in `node_runs` (`NodeRunDto`), `error_code`, `error_meaning` and `withheld`; and `error_code` on a For Each child (`ForEachChildSummary`). A failed step or run now records one catalogue code, and `error_meaning` is the catalogue's one-line meaning of it. An installed app's run blanks a failure's text, input and output for a reader who may not see them; the code and its meaning are platform text, so they stay, and `withheld` lists the fields that were blanked while they held a value (a step's `input`, `output` and `error`; a run's `input_payload`, `output_payload`, `name` and `error_message`), so a blank field is not mistaken for an empty one. All of these are optional and absent when empty, and a platform build that predates failure codes never sends them.

The skills describe more of what a workflow meets at run time: which version a run used and that a deployment awaiting approval changes nothing, diagnostic steps for a failure whose text is withheld, a For Each over files (which sources hand the child a typed file), what a For Each child reads from its parent, strict Code inputs and empty literals, what a search hands an agent with a read limit, `_citations` in Agent output, and a file belonging to one record.

A For Each over `subject.record.<file field>` hands each child a typed file, so `{{ input.<itemAlias> }}` and `content(...)` in the child's Agent prompt read it; the skills list it among the typed sources.

In a Python Code step, `"x" in inputs` answers `False` for an undeclared input instead of raising; the skills say so.

An Agent step refused by its read limit names a computed field as computed, not secured, and says what each needs.

`lit("")` is written as an explicit empty string (`valueJson: ""`), so a Code step input bound to it is no longer refused as `code.input_unbound`; `lit(null)` needs an AgentFlow build that reads an explicit `null` as a value. An install plan's finding from a workflow publish now carries the validator's message. The skills say so.

`agentflow-app build` refuses a Code step whose file reads an input the step does not declare (`inputs.x`, `inputs["x"]`, Python's `inputs.get("x")`, a destructuring of the inputs), naming the file and the names; such a read throws `CodeInputError` at run time. A read the file guards with `"x" in inputs` is accepted.

`agentflow-app build --check --values` compares `package/` with what the config builds as JSON values, member order aside, writes nothing, and refuses `PACKAGE_DIFFERS` (exit 1) naming each member that differs as `<file>#<pointer>`. Rewriting a converted workflow with the helpers is checked with it; the from-draft skill no longer has you copy `package/` aside and paste a comparison script. `checkPackage(dir, { values: true })` is the same check.

`agentflow-app deploy` says what stops its approval. It prints whether the installed version keeps running until a person approves the deployment, and the findings a person's plan stored. `deploy --wait` stops with `DEPLOY_NOT_APPROVABLE` (exit 1), naming the findings, once a plan finds the deployment cannot be approved for a reason other than a setup answer the admin still has to give; the deployment stays awaiting approval. `deploy --sandbox` prints the plan's warnings, such as an agent's read limit a step does not cover, and returns them as `plan_warnings` under `--json`.

`deploy --sandbox --upgrade` refuses `SANDBOX_ELSEWHERE`, before any request, when `AGENTFLOW_URL` names another AgentFlow than the one the recorded sandbox was made on, rather than calling that sandbox gone; and its "upgraded a to b" line takes the old version from the deployment, so it stays right after an interrupted upgrade or an uninstall.

A replayed `deploy --sandbox --upgrade` of a version the sandbox already finished installing says "was already installed" rather than "upgraded", since that run installed nothing.

Editing a package's typed literal (`lit(42)`, `lit(true)`) in the designer's Entity Record step keeps its type: the cell's text is parsed as JSON, as Set Variable's literal cell parses it. It was saved as text. A literal that held text stays text.

`agentflow-app deploy --sandbox --upgrade` installs a new version into the sandbox `.agentflow/sandbox.json` records, instead of deleting it and making a new one, so its records and the organization settings set there by hand stay. It sends the install answers recorded when the sandbox was made, and refuses `SANDBOX_GONE` when that sandbox expired or was deleted.

A search step can name the fields it returns: `search(id, name, entity, filters, { fields: ["title", "status"] })` returns each record's `id`, `metadata` and those fields only, and only they count against an agent with a read limit that reads the result, beside the fields the search filters, sorts or searches on. Publish refuses a name the entity lacks. It needs an AgentFlow build that reads `fields`; an older one returns whole records. The skills say so.

`bind(field, source, { copy: true })` gives a record its own copy of a file another record holds, such as each file of a parent's file field written to a child record in a For Each; without it the write is refused, as before, and the refusal now says to mark the binding copy. The run must be able to read the record that holds the file, and a file in a secured field is copied only into a secured field. It needs an AgentFlow build that reads `copy`. The skills say so.

A step that fails the same way on every attempt, such as writing a file another record holds, now fails its run on the first attempt rather than after three; children of a parallel For Each that each create a record referencing the same record no longer fail intermittently. The skills say so, and keep the old behaviour as a note for older AgentFlow builds.

An `expect` with an empty value now holds when the field is empty: a value that is empty after trimming, including one a step read earlier that was empty, is an expectation of an empty field. So an update with `expect: { fields: { claimed_by: "" } }` skips once someone holds the record, which closes the gap the skills used to warn about. On an AgentFlow build from before this change a field with no value never matches, not even `""`, so such an update skips every time there. `work.md` and `steps.md` say so, and the pitfall "An update with `expect` skips every time" is gone.

A Human step can end itself on a condition, with `endWhen`: a condition over `subject.record.<field>`, written with a Decision's operators, checked when the step opens and after every change to the record. `label` is the outcome it records, and `then` takes one of the step's actions or a branch of its own, read downstream as `output.action == "__condition_met"`. A condition already true when the step opens settles it with no task and no notice, and a condition that cannot work is refused at publish and at install with `human.end_when_invalid`. The skills describe it in `workflows.md` beside `work` on the entity, as the second way to let a change outside the run finish a task (`work.md`, `pitfalls.md`). `build` counts the edges an `endWhen` branch names as the Human step's own, beside its actions' edges.

An entity can carry starter records, with `seed`: a list of literal record bodies that the install creates once per natural key, at most 1,000 in a package. The app builder copies `seed` as written, and refuses a value that is not a list, a body that is not an object, a `${…}` reference, a leading `@`, and more than 1,000 in one file. An upgrade or a reattach seeds only keys it has not seeded, so an admin's edit or deletion stands, and undo removes the starter records nobody touched. Starter records wait while a natural key the same release adds is still being built, and the next upgrade or reattach seeds them, so a key and its starter records are faster in two releases. An AgentFlow deployment from before seeds refuses the whole package. `entities.md` ("Starter records: `seed`", and a section on starter records an app creates itself), `pitfalls.md` and `sandbox-testing.md` ("What a sandbox holds") say so.

A module can read a record's runs and what each run did. The generated API types gain `list_record_runs` (`GET /entities/{entity_id}/records/{record_id}/runs`, a page of run headers newest first, for anyone who can read the record) and `get_run_trace` (`GET /instances/{instance_id}/trace`: each step's label, kind, status, timings and attempts, and for an agent step its skills, a count per tool and the memory it drew on, counted by type). Neither returns error text, token counts, inputs, outputs, prompts or memory titles. Through an installed app only runs of covered workflows are told, and a run about a record is traced only if the app can read the record. The generated types also catch up on entity sources (`EntitySourceView`, `SourceState`, `Entity.source`), which they had fallen behind on. `records-api.md` ("A record's runs, and what a run did") describes both operations.

An entity's `work.module_page` names the page of the package's module its records open at from My Work: a path holding `{{ record_id }}`. It needs the package's `ui` and the entity's `work_surface`.

A module can read what each agent its package installed did over a window. The generated API types gain `get_app_agent_activity` (`GET /app/agents/activity`, for an installed app only) with `AppAgentActivity`, `AgentActivity`, `AgentActivityAgent`, `AgentActivitySteps` and `AgentActivityLearn`: for every agent the package installed, in key order, the steps that succeeded and failed and the Learn counts proposed, created, confirmed and dropped, over a window of at most 92 days (the last 30 days when `from` and `to` are absent). A retried step counts once, by its last attempt, and a step falls in the window of its first call. Only runs the person could see through the app count. Nothing a run took in or produced is told. `records-api.md` ("An app's agents over a window") describes the operation.

## sdk-v0.5.0

configVersion: 1
formatVersion: 1
minPlatformVersion: 2026.10
Skills dry run: 2026-10-27, one pass on a fresh copy of the template made from this branch's SDK (a local mirror tagged sdk-v0.5.0, installed by git reference), replayed on the final SDK — agentflow-app-authoring, agentflow-app-release, agentflow-ui-module and agentflow-from-draft (a help desk, `acme/help-desk`, written from the skills alone: three entities, a `known_issue` memory type with grants to everyone and to an optional reviewer group, an `affects` relationship, a `triage` agent with a `read_limit` over the entities and the type and a `memorySave`, a Learn step started by a "status becomes resolved" trigger, and an Agent step with a `memory` block started by a `created` trigger; `init --no-site --no-ui`, `build` with the memory refusals the skills name, `types`, `build --check`, `lint` through AgentFlow's own lint rules run offline (`app-package lint`, as the lint route runs them) with its `learn_read_limit_uncovered`, `keygen`, `seal`; the UI starter through `init --no-site`, `build`, `test`, `typecheck` and `types --check`; and the package as a draft through `init --from`, rebuilt to the same package); 7 findings, the fixes are in this release; not covered: `lint` against a running deployment, the sandbox loop, `deploy`, the install plan, `status`, `publish`, a Learn run and recall, and anything in AgentFlow's web pages (there was no deployment and no browser).

An app can now carry an agent's memory. This release needs an AgentFlow build at or after PR #691, which installs what a package writes here; against an older build the SDK still builds the package, but that build refuses a package that carries the new members (its version check passes, since `minPlatformVersion` stays 2026.10). The skills have the details (`agentflow-app-authoring`, `reference/memory.md` and `reference/agents-and-skills.md`).

Read limits: an agent file may carry `read_limit`, `{ "entities": [{ "entity": "${entity:<key>}", "operations": ["read", "list"] }], "memory_types": ["${memory_type:<key>}"] }`, the records and the memory types the agent may read. `entities` is required (and may be empty), an entity is one the package declares and appears once, and a memory type has no operations: a listed type is read. Installing turns the agent's limit on and grants exactly those pairs; an agent without one is left as the organization has it, and an upgrade keeps what the admin removed (the plan says so with `read_limit_withheld`). `lint` reports `read_limit_invalid`, and the plan warns with `agent_read_limit` where a step needs a field no profile gives.

Memory types and relationships: `build` reads `config/memory_types/<key>.json` and `config/memory_relationships/<key>.json` and writes `objects/memory_type/<key>.json` and `objects/memory_relationship/<key>.json`. A type has `name`, `describe`, `fields` (a closed schema of single-valued fields: text, number, boolean, date, or a choice), `title`, `review`, and optionally `search_on`, `recall`, `max_per_about`, `expire_after_days`, `never_store`, `grants` and `deprecated`; a relationship has `name`, `description`, `from`, `to`, `review` and optionally `attributes` and `deprecated`, and each end is an entity or a memory type of the package. They are named `${memory_type:<key>}` and `${memory_relationship:<key>}`, of the package's own objects only, and a memory type and a relationship share one key space. `grants` says who reads a type's memory or reviews its proposals: `"everyone"` or `${param:<key>}` of a `group_ref` parameter (never a literal group id); left out, a type is read by everyone, and an optional group parameter the admin leaves unset withholds its grant (`memory_grant_withheld`). The plan shows the admin each grant it writes (`memory_grant_written`). A package carries definitions, never the memory itself. An upgrade never deletes a definition: one removed from a later release is archived, `"deprecated": true` archives one that is still shipped, and a change that memory already stored forbids is blocked as `APP_MEMORY_DEFINITION_FROZEN`. Undo is blocked while memory exists in a type the installation created. `agentflow-app types` leaves memory types and relationships out of `OBJECTS`, as agents and skills are, and `init --from` converts a draft that holds them.

Saving memory: an agent's `profile.memorySave` (`types`, `relationships`, `about`, `orgWide`, `review`, `instructions`) lets it save memory in a conversation, and in an Agent step that names it. The build refuses an agent whose `read_limit.memory_types` does not list every type it saves into, and the type ends of the relationships it saves, at `/read_limit/memory_types`; `lint` reports the same gap as `memory_save_read_limit_uncovered`. The plan names each such agent to the admin before approval (`memory_save_declared`), since it will write memory. A chat save is proposed for review when `memorySave.review` is true (off by default); otherwise, and in a step, the type's `review` decides, and an item about nothing is always reviewed.

The Learn step and the `memory` block: a package may now ship a `learn` step, which reads one record and the records that hang off it and writes what it finds into the package's own memory types and relationships (`learn.types`, `learn.relationships`, written with the keys above), through an agent of the package whose `read_limit` covers what the step reads: the builder has no helper for it, so write it with `node(id, name, "learn", { … })`. Verification refuses a Learn step that names another agent, an agent without a limit or a read the limit does not cover (`learn_agent_not_own`, `learn_read_limit_missing`, `learn_read_limit_uncovered`), and a relationship end the step cannot bind or a deprecated type (`memory_reference_invalid`); `learn_step`, which refused every Learn step, is gone. Everything else about the step's fields is judged when AgentFlow publishes the workflow, at install, and the setup page lists the findings, so install a Learn step in a sandbox before you send it to an admin. An `agent` step may carry a `memory` block (`about`, `hops`, `maxNodes`) that recalls memory about the records it names before the model starts; it names record paths, not memory types, so a package ships it, and the agent reads memory through its `read_limit.memory_types`. An agent reads an item only when its `read_limit` has both `read` and `list` on the record the item is about and on the records it was learned from, so give a Learn step's source and About entities `list` as well as the `read` verification asks for.

`search_on` of a memory type names text or choice fields, and the builder now refuses a field of any other kind (a number, a date), as the platform does.
